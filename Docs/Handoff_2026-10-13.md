### New-game load 24.5 s -> 7.1 s (afternoon): far voxel chunks were looking for lakes smaller than one of their voxels
**Diagnosis:** the generator's water pass (`FMOWorldGen::ApplyWater`) resolved every basin tier at every LOD. A far voxel chunk samples ~1 km apart, so each sample landed in a different upland-lake cell and ran `ComputeUplandLake` (hundreds of full-detail base samples) for lakes ~260 m across -- invisible at that spacing. A 32 km LOD-11 chunk took 5 s to mesh; meshing groups chunks by column and runs a column serially, so two such chunks made the voxel world's second state take 10.4 s on ~3 cores, and every PCG chain waits for the voxel state (`WaitForVoxelWorld`). The first full state cost 2.3 min of CPU for the same reason.
**Fix:** `FMOWorldGen::IsWaterTierResolved(Params, Tier, StepCm)` -- a tier is resolved while its largest radius is wider than the sample spacing (the octave rule, wavelength < 2 x step, applied to a basin's diameter). `ApplyWater` takes the step and skips unresolved tiers; the terrain node paints the lake-bed surface only where the tier is resolved. `MO.WorldGen.DebugNoLodCull 1` still resolves everything.
**Evidence (packaged, seed 1029024224):** READY **24.5 -> 7.1 s at 1920x1080**, 25.2 -> 7.1 s at 960x540, 7.3 s on a third run. Full voxel state 8.2 s / 2.3 min CPU -> 0.8 s / 12.6 s CPU; the 10.4 s second state -> 0.3 s. Census within 100 m of spawn: 7916 instances, unchanged (sink / tilt unchanged). `MOFramework.PCG.SampleCosts` COARSE CHUNK: the LOD-11 chunk's 1089 columns in 0.6 ms. Test `MOFramework.WorldGen.WaterLodGate` (rule per tier; a real upland lake carves at the voxel size and is absent past every tier's spacing). Shots from 1.6 / 6 / 12 km and a 1.5 km-high overview: the near lake shows water in its bowl with the bed rim, the far terrain shows no pits (`Saved/StagedBuilds_DevTest/Windows/MO57/Saved/Screenshots/Windows/HighresScreenshot0000{0..3}.png`).
**How it was found:** `voxel.LogStateTime 1` (state wall vs CPU time) + `-DumpVoxelStatus` (pending voxel tasks) + a new local diagnostic in the voxel plugin, `voxel.render.LogSlowChunkMs <ms>` (logs every render chunk / meshing column slower than that: LOD, key, bounds). The readiness trace now also prints `voxelNewState` / `voxelPending`.
**Negative result:** bypassing `WaitForVoxelWorld` on the near tiers (`Content/Python/bypass_voxel_wait.py`, report-only now) changed nothing (READY 24.6 vs 24.5 s) -- the near cells arrived with the voxel state either way. Reverted.
**Found, not fixed:** (1) ~20 s after READY the SpawnManager's first survivor / deer spawns start a voxel state of 2.7-5.4 s wall and 1.2-2.5 min of CPU (224 parallel LOD-0 tasks: the new pawns' navigation invokers) -- background threads, needs a frame-time check. (2) the deer fallback spawn put one deer at Z = -1014 cm, under the sea ("Fallback spawned BP_Deer_C ... (326m from player)"): the fallback does not reject water.

### World removals (felled trees, picked-up items) — fixed the same morning
**Diagnosis:** removing a PCG instance only deleted it from the local component. PCG cells regenerate (walk ~200 m away and back), each co-op machine generates its own instances, and nothing was saved -- so a felled tree or a picked-up stick came back on the next generation, NEVER disappeared on a co-op client, and was back after a load (infinite resources). Also `MOHarvestSubsystem` computed the depletion node key AFTER removing the instance, so a felled tree's yields were charged to its neighbour.
**Fix:** `UMOWorldRemovalSubsystem` + `FMOWorldRemovalLedger` (place in 10 cm cells + mesh name): `FMOHISMHarvestHelper::RemoveInstance` (now the only removal path: Foraging, Harvest, HISMInteractable routed through it) records before removing; the biome and item spawners skip recorded places; `AMOGameState` replicates the record (FastArray: clients remove their own copy, late joiners get it all); `IMOSaveDomain` saves / loads it. Removals are permanent -- **regrowth over game time is a design question for Wes** (realistic litterfall / sapling regrowth would be slow).
**Evidence (packaged):** `MO.Test.RemovalPersists` PASS (felled sapling stays gone through `pcg.RuntimeGeneration.Refresh`, neighbours return); its `control` mode (removal NOT recorded) FAILS as it must (the sapling comes back -- the original bug, reproduced); `saveload` mode PASS (after save + load + regeneration the loaded record holds it); `nettest packaged-removal` PASS (the host fells, the client's own copy is removed: `[MOWorldRemoval] removed 1 spawned instance(s)`); test `WorldRemoval.Ledger`. Co-op baseline `nettest packaged` PASS; its clock check no longer flakes (the client logs its first host clock sample; the snap line alone only appeared when the drift exceeded 1 game-s) and it waits for the client's possession before its observation window (a slow seed's 45 s coastal settle read as "never possessed").

- **note: snow is one global altitude line** (`SnowLineCm` 1250 m) on the terrain only.

## Efficiency (what cost the most time)
- **Six editor restarts at ~4 min each**, for C++ builds and two crashes.
  - Batch C++ edits.
  - Content edits do not need an editor restart.
  - The `ui` instance runs fine next to the editor for VISUAL checks, but never for perf: they share the GPU.
- **After a crash the bridge never comes up**, because the editor sits on the package-restore dialog. Run `ue.py editor stop`, move `Saved/Autosaves` aside, then start again.
- **Python API traps:**
  - Struct array elements read from `get_editor_property` are copies. Rebuild the structs and set the whole array.
  - `MaterialExpressionSetMaterialAttributes.inputs` is protected. Use Break/Make MaterialAttributes.
  - Bash heredocs containing `'''` break. Write patch scripts with the Write tool.
- **Sky:** `MO.Clock.SetTime` only moves the sky forward in game time. Use `MO.Weather.Director 0` + `MO.Weather.SetPreset Clear_Skies` for stable shots, and `r.VolumetricRenderTarget 0` for 4K clouds.
- **Find what an artefact is made of** with `MO.PCG.MeshSurvey`, `MO.PCG.HideMesh` and `MO.PCG.HideTag` before guessing. That is how the native Field_05 trees (90 k, biome-blind) turned out to be the "speckled far forest", after an hour spent blaming the biome tiers.
